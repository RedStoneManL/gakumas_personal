# Colab 长时间训练包

把包旁边的 `HIF_Training.ipynb` 上传到 Colab，选择 GPU 运行时，按顺序运行。
Notebook 会挂载 Google Drive、接收 `gakumas-colab-training.zip`、检查完整性、
在本地磁盘安装 Arena 和新训练器，再做真实引擎与模型预检。

外置的 `HIF_Training_v4_cached_preflight.ipynb` 可直接搭配原 v4 ZIP，保持原
`RUN_NAME` 续训，无需迁移。第6格默认查找该运行目录下旧会话已通过的完整
preflight 报告；包清单、配置、Python/Node/PyTorch/CUDA版本、GPU型号与总显存
均一致时复用，每次只在独立训练环境执行小型CUDA前后向。旧版完整报告也可
直接复用，无需为建立缓存再跑一遍。报告记录原路径与哈希，并明确区分历史
完整检查和本次快速检查；换环境、配置、训练包、缺少完整记录或使用外部主数据
覆盖时自动重做。第6格 `FORCE_PREFLIGHT=True` 可主动重跑。首次基线评估和训练
中的定期评分不受影响。Notebook为独立启动入口，不修改已验证ZIP内的源文件。

五套编成各自的机制、开局属性/成长/牌组/固有物品，以及五场试镜回合数
和排列依据见包内 [编成与试镜数据](LOADOUTS_AND_COURSES.md)。其中回合配额
保存于本地固定研究快照，排列概率等近似假设与主数据字段分别标注。

默认累计训练 **24 小时**，每次会话主动运行约 **8 小时**；时间在完整 PPO
更新边界检查，因此可能超过设定时间一个批次。24 小时指累计运行预算，
不保证 Colab 提供一次连续 24 小时的 GPU。断开后重新打开相同 Notebook，
使用同一个 ZIP、配置和 `RUN_NAME` 即可恢复。训练从随机参数开始。

| CONFIG_NAME | 内容 | 每次更新 / 独立评估局数 |
|---|---|---|
| `full_produce` | 固定六支援「ガラクタロード·广」，从头培育到终止 | 8 / 8 |
| `full_produce_mixed` | 五偶像轮换，支援和回忆使用给定配置 | 10 / 10 |
| `full_produce_select` | 五偶像轮换，由模型先选支援和回忆，再完成培育 | 10 / 10 |
| `full_produce_setup_mixed` | 默认：五偶像 × 给定 / 自选两模式均衡训练，共用一个模型 | 10 / 10 |
| `exam_score` | Arena 内置 HIF 第二轮考试起点，独立训练纯打分模型 | 16 / 8 |

混合配置的准确游戏 ID 在 `configs/full_produce_mixed.json`；`ume-campus`
是花海佑芽（`i_card-hume-3-006`）。五套配置按流派选用合法的六支援作为
可复现的训练起点：保留两张通用支援，其余按原槽位属性和稀有度替换为
对应流派的支援，并非为每位偶像优化过的编成。培育配置均为 PLv76、
rank6、亲爱度37，成长面板等级见 JSON。给定模式目前没有携带回忆。
自选模式从 `configs/research_inventory.json` 的明确研究候选中选六张支援、
最多四张回忆；这些候选也完整嵌入对应训练配置，不需要另传第三个文件。
该池使用研究环境授权的数据，不代表用户账号拥有库存。最终候选范围、
来源和排除项见 [研究候选池规则](RESEARCH_POOL.md) 及 `validation/` 中的验收记录。
研究回忆使用分解选择：携带卡身份、卡片变体、可选HIF能力、三个金色普通
因子分别由模型决定，最多组成四张回忆。它们是明确的研究构造，不声明
每一种组合都能在实机生成。配置中的槽位预算、跨Plan排除与能力限制仍
然必须满足，不能把携带卡与某种HIF目标预先绑成同一个候选来替模型选择。
开训前先做一次独立基线评估，之后默认每 5 次更新评估一次；训练与评估
使用不重叠的种子，同一编成的评估种子保持一致。

五偶像为咲季 Wildest Flower、咲季/广 ガラクタロード、佑芽 Campus mode、
莉莉娅 White Night。偶像选择始终由环境控制，策略不能自己选广。
`full_produce_mixed` 和 `full_produce_select` 每10局每偶像各2局。
默认 `full_produce_setup_mixed` 每10局覆盖五偶像×两模式各1局；它用
`seed % pool_size` 选偶像，用 `(seed // pool_size) % 2` 交替给定 / 自选，
断线恢复后仍按相同进度采样。评估种子也覆盖同样十个组合。
一个 PPO 模型处理配置、外层选择、培育中间选择和打牌决策；给定模式
直接跳过配置阶段，自选模式的配置动作与培育动作属于同一个完整 episode。
所有开局属性、体力、牌组、有效支援/P 道具机制和考试规则来自实际引擎
状态。知道新编成的输入，并不意味着已经学会它的策略。

默认运行名称是 `hif-setup-mixed-v4`。配置阶段的熵奖励系数明确为 **0.05**，
普通决策为 **0.01**，鼓励支援/回忆选择保留更多探索。动作仍从同一策略
分布采样并记录实际概率，没有额外注入随机动作。PPO 的策略和值损失没有
按阶段重新加权；gamma=1，中间奖励为0，所有动作的回报都是最终原始评价
除以固定 C=50000。探索更强并不等于一定能在24小时内学会复杂组合。

训练使用完整 episode 的最终评价，固定缩放后交给 PPO。中间不额外奖励
体力或分数。选拔失败采用已明确命名的 `final_formula_zero_unplayed_v1`
训练约定：把未进行的最终考试分数置零，代入最终评价公式；这不是声称
游戏实际在选拔失败时发放这一评价。引擎错误不会被伪装成低分样本。

## 保存、恢复与停止

- 持久化目录为 `MyDrive/gakumas-runs/RUN_NAME/`。每次完成参数更新后提交
  checkpoint，保留模型、优化器、词表、随机状态、种子进度和累计时间。
- Drive 采用带哈希的版本化快照与提交记录，保留最近三个有效版本；
  重启会恢复可校验的最新提交。上传中途断线最多回退到前一有效提交。
- 运行中可在该目录创建一个名为 `STOP` 的空文件。程序在完成当前批次并
  保存后停止；继续运行前删掉这个文件。直接中断可能丢失当前未提交批次。
- 保留相同 `RUN_NAME` 才是断线续训；更换任务、编成池、超参数或代码需要
  新实验名。当前入口不把修改配置后继续训练包装成严格恢复。
- 从给定模式切换到自选 / 混合模式属于新实验，不能用原名称修改配置后
  resume；只有明确实现并核验的参数初始化流程才能迁移旧模型。默认均从
  随机参数开始，原给定模式交付包可继续使用其自身代码与配置恢复。
- `full_produce` 和 `exam_score` 是两个独立训练任务；不要共用实验名。
- 时间可以在下一次会话增加，例如把累计预算改为72小时；不会重置已有进度。

## 显存和日志

建议先选择 Python 3、A100 GPU、High-RAM、Latest。当前实现使用 PyTorch CUDA，
TPU不能直接替代GPU。High-RAM是系统内存，有助于容纳并行环境和轨迹；实际GPU、
可用资源及计费以Colab会话为准，A100的实测性价比不能仅由硬件名称确定。

图网络仍为宽度64、两层。Notebook首次运行会封存基础配置：`WORKERS=auto`
按可用 CPU 核数取进程数，6核以上为主进程留2核，较小CPU配额按核数限制；
`PPO_MICROBATCH=auto`在约16GB／24GB／40GB／80GB显存上分别取2／4／8／16。
例如A100 80GB、12核采用10个worker和microbatch 16。这是起点，不是该型号实测的最佳值。
预检执行最大已观测图的GPU前后向，启动探针最多32图，OOM会缩小探针批次；
报告区分请求值和实际测过的值，较大运行批次另有激活OOM回退。
首次可手填任意正整数的环境进程数和 microbatch，没有应用层固定上限；若初始micro超过64，
初始minibatch同步提高。自动初值仍使用minibatch64，网络、学习率、奖励不变。

2个及以上worker使用独立Arena/Node进程，主进程统一管理词表和GPU批量推理。
按固定worker顺序同步收齐决策再推理，完整episode收齐后才做PPO更新；采样期间
策略冻结，不使用跨版本旧轨迹。单worker保留原执行路径。静态机制树和图张量
使用有上限的缓存，不把整个训练历史永久留在内存或GPU中。

v3把模型每次前向需要的树分层、父节点分组和每图节点区间提前在CPU物化，
GPU使用固定整数索引和连续切片，避免动态布尔索引/unique造成的同步等待。
网络参数、数学运算和输入语义不变。本机RTX 5080短测的考试双图前向
13.90→8.66ms，编成/考试混合四图61.56→28.03ms；同权重log-prob差异为0，
梯度对照通过。它们是模型前向结果，不是Colab或整局训练速度保证。
详见 `validation/policy-topology-optimization.json`。

基础配置保存在 `MyDrive/gakumas-runs/_performance_configs/RUN_NAME.json`。
运行中的四项性能参数另存检查点，不改变运行身份或重置学习状态。

第7格在后台启动一个受管理的训练进程并立即返回，日志面板每2秒刷新，展示最近
200行并把完整日志保存到Drive。第8格可反复填写并提交：

| 控制字段 | 范围 |
|---|---:|
| workers | 正整数，无应用层固定上限 |
| episodes_per_update | 正整数，无应用层固定上限 |
| minibatch_size | 正整数，无应用层固定上限 |
| microbatch_size | 正整数，且不超过minibatch |

请求写到 `_runtime_controls/RUN_NAME.json`。worker和局数在下一次采集边界生效；
mini/micro在下一次PPO更新开始前生效。不会中途打断正在运行的批次。
不改网络、学习率或奖励。控制文件错误会保留上一组有效设置并在面板显示原因。
五偶像混合任务建议每批局数用10的倍数；任意数量也会按连续种子保持长期轮换。
worker实际启动数量不超过当前待采集局数；固定10局的基线评估最多同时10局。

CUDA激活OOM自动缩小micro并重算当前优化器minibatch；此前成功的优化器步骤
不会重复执行。推理OOM会拆分前向，仍在完整批次上统一采样。退档值会显示，
PPO有效micro写入检查点；同一旧请求不会每轮自动把它拉高，重新提交可主动再试。
单图仍OOM、优化器自身OOM及系统RAM不足不会被伪装成成功训练，恢复使用最近完整检查点。
实际规模受可用内存、操作系统和计算资源约束，较大rollout尤其会增加CPU内存和一次保存前的等待时间。
第9格可请求安全停止；不要通过重复运行第7格创建第二个训练进程。

旧包升级可在新Notebook第5格填写 `MIGRATE_FROM_RUN`，`RUN_NAME` 使用新名称。
迁移允许这四项性能参数变化，严格校验任务、引擎、网络、编码和其他训练参数相同。
复制最近完整的模型、优化器、词表、随机状态、种子进度、日志和累计时间，旧目录不变。
新批次布局不承诺逐位一致轨迹；新运行保留迁移来源，后续恢复不重复覆盖已有进度。

每局日志保留编成、配置模式、实际六支援 / 回忆 ID、完整回忆spec、最终评价、结束阶段、
考试次数与耗时；训练和评估都逐局输出，采集完成后输出参数更新进度。
更新日志区分采集、编码、批量推理与参数更新时间；用每秒有效决策、每小时完整
培育数量及同口径评估改善判断优化，不能单看GPU利用率。Notebook 分别显示训练采样
和独立评估曲线，再按 given / select 和偶像分开，列出相对初始基线的变化。
自选评估的变化包含配置与操作两部分；给定评估衡量在指定编成下的操作。
不同偶像的强度不同，应比较相同偶像、模式、留出种子的前后分数，不能
用跨偶像原分排名或训练时的单次高分判断策略质量。

探索诊断按 `setup_support`、`setup_memory` 及回忆组件阶段、其他决策种类显示
`H/log(合法候选数)` 和采样近似 KL；归一化熵接近1表示更均匀，接近0表示
更确定。同时记录每类候选数、唯一采样数与优化观测数。后者可能因多轮 PPO
重复观察而更大，不代表采集了更多局。最终装备频数按模式分别汇总，
包括单候选自动完成的槽位；选择频数本身不是组合优劣排名。
Notebook 同时展示配置组件选择频数和最终装备频数。合成回忆 ID 是组合
摘要，具体携带卡、获得阶段、定制和能力记录在每局 `episodes.jsonl` 的
`metadata.selected_memory_specs`，Drive 压缩日志保留这四份完整对象。

给定模式覆盖五套明确编成；自选模式扩大到研究池中实际可选的支援 / 回忆
组合，但没有穷举全部组合。未见偶像和未见组合需要独立评测；改变候选池
需使用新实验名。最初给定池的20种考试P道具、420个卡牌变体、28种饮料
身份映射盘点保存在 `validation/`，这个数字不能冒充扩大研究池的覆盖数量。
扩大支援范围后，`s_card-3-0087` / `pitem_01-3-305-0` 的主数据与原生名称
差异已修复并测试。`validation/support-mapping-audit.json` 记录全部201支援
涉及的50种考试P道具和228个奖励卡升级变体均有映射；研究携带卡的1062个
版本还通过了实际原生定制转换。身份映射检查不等于所有效果组合均已完成
语义回归。
这是训练软件和数据包，未附训练好的策略，也不保证24小时后达到指定水平。
交付前的验证结果是本地真实引擎与短程训练验证；实际 Colab GPU 环境由
Notebook 的预检检查。Colab 的资源和最长会话限制参见
[官方 FAQ](https://research.google.com/colaboratory/faq.html)。

## 包含内容与复现

断线后先用 `artifacts/colab/HIF_Debug.ipynb`（相对 training 目录）。它只需 CPU
和挂载原 Google Drive，填写原 `RUN_NAME`，无需训练 ZIP 或旧 kernel 变量。
它读取 `_session_diagnostics/RUN_NAME/*/training-console.log` 的末尾、最近保存
的 PPO iteration、状态及评分，并可下载 JSON 报告。快照 generation 是保存版本，
不能当作训练轮数；历史 PID 和空 returncode 也不表示旧 VM 仍存活。诊断不加载权重，
正式恢复仍由训练入口验证完整检查点。

`artifacts/colab/HIF_Training_v4_diagnostics.ipynb` 可继续使用原 v4 ZIP 和原运行名，
保留预检缓存，并在第7格启动独立资源记录器，每15秒记录进程树 PSS/USS/RSS、
系统可用内存、GPU 和训练边界状态。记录保存在同一诊断目录下带唯一后缀的
`resources-*.jsonl`；观察器不导入模型或改变训练参数。新诊断工具按轮次与阶段
汇总已有资源记录；旧版本未记录的 RAM 峰值不能事后找回。训练进程被杀时观察器
会尽量记录消失事件；整个 VM 被回收或 Drive 中断时，最后几条仍可能丢失。
这次只增加诊断入口，没有修改冻结 ZIP、训练算法或修复尚未确认的内存泄漏。

`arena/` 包含对应版本 Python、Node 引擎、vendor 和原始主数据；`training/`
包含新 PPO 训练器；`colab/` 是入口、预检和保存逻辑；`configs/` 是长训配置。
未打入 Windows 虚拟环境、旧训练目录、账号信息或旧模型权重。
Arena 包括 GPL 上游组件，其许可证及 provenance 随包保留。

在原工作区执行 `python rl/hif-colab/build_training_bundle.py` 可重新打包。
执行 `python rl/hif-colab/build_training_bundle.py --verify ZIP路径` 可验证。
相同源文件产生相同文件清单；每个文件都有 SHA256。
